# Hylsia Privacy Pools — v0.1 implementation (Robinhood Chain Testnet)

Implementation of the *v0.1 concept specification (13 November 2026)*. This document records
what has been built, design decisions, trust boundaries and the steps for running each phase.
Status: **the Robinhood Chain Testnet pool is live; unaudited; test ETH only.**

Hylsia is a privacy pool built for Robinhood Chain Testnet. Deposits and withdrawals happen on the
same chain; the hidden information is their connection, not the deposits or withdrawals themselves.
Mainnet and assets other than native ETH are outside this testnet release's scope.

## Phase 6 review (19 November 2026)

**H-01 blocks release**: cross-profile/device note-derivation reuse can leave a second deposit unable
to withdraw or ragequit after its nullifier is consumed. Real-proof reproduction, local tab-coordination
fixes, test results and limitations: [findings](../security/findings.md). No independent audit.
Phases 7–9 are prepared but unexecuted: [release checklist](release-checklist.md). Active contracts,
circuits, keys, verifiers, manifests and records are frozen; all 37 SHA-256 digests remain unchanged.
The runtime does not require the owner key.

Eligibility is not inclusion: a deposit becomes eligible one hour after its block time, then waits for
a root that includes it. The 1 hour–1 hour 10 minute estimate assumes an active, funded, healthy publisher.
Historical statements that ragequit is always available require an unspent note, a matching proof,
the original depositor wallet and gas, and no H-01 nullifier reuse. Exiting change reveals its original
label and may link a partial withdrawal. A seed backup reconstructs onchain notes/balance; it does not
automatically retain the complete local activity history. Crowd figures count deposits, not independent
people; Strong is an application model, not a guarantee.

### Server

- One server process serves every environment-listed network, normally only Robinhood Chain Testnet. Event,
  block-time and publication-status caches are keyed by (chainId, pool address); each `privacy.*` response
  contains one entry per pool with `now` taken from its own chain.
- **Contract checks** before reading or writing a pool: `eth_chainId` must match, the pool address must
  contain code, and `SCOPE()` must equal `computeScope(pool, chainId)` and the deployment record. On failure,
  the pool is *unavailable* and no transaction is sent.
- **Isolation.** A dead or hanging RPC makes only its pool *unavailable*. Each server RPC call times out
  after 5 seconds, with at most two attempts. Calls spanning all pools (`privacy.networks`, `pools`,
  `poolActivity`, `asp.status`, `asp.set`, `asp.publish`, `poolDetail`) impose an 8-second per-pool deadline:
  a pool exceeding it is reported *unavailable* (`rpc_error`), below Vercel's 30-second limit. A timed-out
  publication whose send remains unanswered is never submitted twice.
- **Cold scanning.** Robinhood Chain Testnet produces about 420,000 blocks daily; public RPC accepts at most
  100,000 blocks per `eth_getLogs` request. Log chunks are therefore 100,000 blocks; server and device request
  four concurrently in one HTTP batch. Interrupted scans (timeout/disconnection) retain server progress and
  resume on the next request; incomplete progress is never presented as pool data.
- **Reorgs.** Events are rescanned from `lastBlock + 1 − reorg window` (20 blocks on Robinhood Chain Testnet)
  and cached events from that block are replaced. If RPC head falls below the last block but remains inside
  the reorg window (a slightly lagging node), the cache is retained. A larger rollback, or any rollback on a
  local chain without a window (Anvil restart/revert), clears that pool's cache and rescans from deploy block
  on both server and device. The server also clears pending publication records, contract checks, block times,
  funding reads and pool memos, so hashes from the old chain are never returned as `pending`.
- **Startup summary** prints each network's mode, RPC host only (no path/query/credentials), pool, derived
  relayer/publisher addresses (never keys), confirmations and inclusion delay, then exclusion-list state
  (source and entry count, or invalidity reason: entry number and field only, never values/notes), and
  scheduled-publisher state.

## Scheduled publisher (auto-publish)

A new pool has no association-set root. Without one, the first private withdrawal cannot be proved, yet
previously only a withdrawal requested a root. A long-running server (`npm run dev`, `npm start`) now
publishes roots on a schedule (`server/privacy/autoPublish.ts`). Since the Phase 4 review fixes, the form
starts private withdrawals only for deposits already in the newest onchain root. The first root must
therefore come from this schedule or `npm run zk:asp:publish`: with one network, no withdrawal can request
it; with multiple networks, a withdrawal in another network's pool can, since one publish request covers
every pool. Roots adding newly screened deposits come from the schedule, `npm run zk:asp:publish`, or
another note's withdrawal request when a root is due. Serverless hosting without a scheduled publisher
requires a scheduler running `npm run zk:asp:publish`; otherwise a new single-network pool never receives
its first root, and later roots arrive only when requested by a withdrawal.

- Every `PRIVACY_ASP_AUTO_PUBLISH_SECONDS` seconds (default 600; `0` disables; otherwise 10–86400), for each
  pool with a publisher key: if a root is due (`rootDue`: deposits have passed the inclusion delay, or the
  exclusion list requires removals), a new root is sent exactly as for one label-free `privacy.asp.publish`
  request. The first tick occurs about one minute after server startup.
- **Second trigger: exclusion-list edits.** A file-based list (`PRIVACY_ASP_EXCLUSIONS_FILE`) is checked
  every 15 seconds. An edit stable for 30 seconds that names current-root members immediately triggers that
  pool's tick, publishing the removal root about 35–45 seconds after the edit in local measurements,
  rather than up to 10 minutes later. Revoked exclusions wait for the normal tick, as do still-changing
  lists: partially saved edits never trigger publication.
- Empty pools and pools with current roots send nothing; the same root is never sent twice. Unmined
  publication transactions, including those submitted before a server restart, return `pending`.
  Two exceptions: a root with a mismatching record (`cid`) is republished with its recipe, at most once per
  root value per process; and excluding the newest deposit before its delay expires changes no members,
  so the same root is sent once more with a record naming that exclusion (once per root/exclusion/process).
  Only then is that exclusion recorded onchain.
- **Pause (`policy_error`):** sends nothing while exclusions are missing/invalid, a root would exclude more
  than 500 deposits, the chain already contains a newer-policy-version root, or the snapshot fails its own
  checks. The reason is logged once. While the list is unreadable, status shows this process's last valid
  list. After restart without a list there is no such cached copy, but the snapshot retains exclusions
  recorded in the newest root (without reasons or announcements), never reports them revoked, and the
  device continues displaying them as "Excluded".
- Runs only when the publisher can fund one publication, checked before scanning events. Otherwise it
  waits and resumes automatically after funding.
- Errors double the delay before the next tick, up to one hour. Logs record only state changes (root sent,
  funding/policy pause, failure, recovery) and only the RPC host.
- Scheduling depends exclusively on time and operator exclusion-list edits, never visitors or requests,
  so it reveals nothing about users. Usually current roots also reduce withdrawal-triggered publication.
- **Serverless:** the Vercel function (`api/index.js`) never starts the schedule, which also refuses to run
  when `VERCEL` is set because function instances live only during requests. For those deployments, run
  `npm run zk:asp:publish` from a cron scheduler and after each exclusion-list edit
  (`PRIVACY_ASP_EXCLUSIONS_JSON`, without notes).

For the live pool, once the publisher is funded, the first root appears within roughly 10 minutes after
the first deposit passes its one-hour inclusion delay: 1 hour–1 hour 10 minutes after deposit.

## Implemented protocol model

- **One device-held seed.** A random 32-byte WebCrypto seed derives every secret:
  `nullifier(i,j) = Poseidon4(masterNullifier, scope, i, j)`, `secret(i,j) = Poseidon4(masterSecret, scope, i, j)`;
  `i` is the deposit index and `j` the hop (0 = deposit; `j+1` = change note from withdrawal `j`).
- **Contract-determined commitments.** `deposit(precommitment)` with `precommitment = Poseidon2(nullifier, secret)`.
  The contract sets `label = Poseidon2(SCOPE, nonce)` and `commitment = Poseidon3(msg.value, label, precommitment)`.
  A note can never claim value that was not deposited.
- **Scope.** `SCOPE = keccak256(pool, chainid, asset) mod p`. Labels, secrets and context bind to the pool and chain.
- **State tree.** Depth-20 incremental Poseidon2 Merkle tree with 100-root history. Leaves are deposit/change commitments.
- **Association set (ASP).** Depth-20 tree of deposit labels, built offchain; `aspPostman` publishes roots, with 16-root history.
  **Screening policy v1** (Phase 4, `shared/privacy/screening.ts`, identical pure code on server and device):
  - deposits are counted in state-tree leaf order; change-note leaves never count;
  - `n`, the number of considered deposits: the leading sequence with sufficient confirmations (1) whose block time
    plus inclusion delay (`PRIVACY_ASP_INCLUSION_DELAY_SECONDS_<id>`: 3600 seconds on Robinhood Chain Testnet,
    0 on local chains) is no later than the snapshot head's block time; equality includes the deposit.
    `n` never decreases, so increasing the delay never removes members;
  - `x`, excluded leaves: considered deposits named by the operator exclusion list (label or depositor address,
    with reason codes `sanctions`, `stolen-funds`, `fraud`, `legal-order`, `test`);
  - members = first `n` deposits minus `x`; root = the list's Poseidon Merkle root. Removing the last member
    publishes the empty-tree root;
  - **The root record (`cid`) is its recipe:** `hylsia-asp:v1;n=<n>;x=<leaf>,<leaf>;asOf=<block>;t=<unix seconds>;delay=<seconds>;conf=<c>`
    (fixed order, decimal without leading zeroes, strictly increasing `x`, at most 500 leaves). Anyone with public
    events can reconstruct and verify every root's list without asking another party. The root binds only membership:
    the split between "not yet considered" and "excluded", plus `asOf`, `t`, `delay`, `conf`, are operator claims.
    Legacy open-policy roots (`open-testnet-policy:count=N:head=H`, a prefix) remain accepted until a screening root exists;
  - deposits listed before eligibility never enter a root. Members listed later leave through the next root;
    revoked exclusions rejoin through the next root without a new delay.
  `shared/privacy/associationSet.ts` builds device-side membership proofs using this module.
- **Withdrawal.** The circuit proves note ownership, state-tree membership, ASP-tree label membership,
  `withdrawnValue <= existingValue` (128-bit range check), `nullifierHash`, and the change commitment
  `Poseidon3(existingValue - withdrawnValue, label, Poseidon2(newNullifier, newSecret))`.
  Public signals: `[newCommitment, nullifierHash, withdrawnValue, stateRoot, ASPRoot, context]`.
- **Authorization binding.** `context = keccak256(abi.encode(SCOPE, recipient, relayer, fee, deadline)) mod p`.
  Changing destination, relayer, fee or deadline invalidates the proof (`ContextMismatch`). The contract checks the deadline.
- **Ragequit.** An ASP-independent exit: commitment proof with public `value` and `label`; only that label's
  original depositor may call it. The deposit → exit link becomes public. It works after `windDown()` without an ASP root.
- **Administrative powers (disclosed).** `owner`: `windDown()` (stops only new deposits), `setASPPostman`, `setMinDeposit`,
  `transferOwnership`. `aspPostman`: `updateASPRoot`. No proxy/upgrade, withdrawal pause, access to user funds or `receive` function.

## Privacy and trust boundaries

The section 07 visibility matrix and section 06 component table are reproduced in the application's
*Privacy & trust* tab and implemented in code:

- The server receives only proofs + public parameters (`server/privacy/relayer.ts`, Zod validation in
  `router.ts`; no secret storage).
- **Association-set proofs are built on the device.** During withdrawal, the browser reconstructs the
  *newest* root's membership (`currentASPRoot`) from the recipe in its `ASPRootUpdated` event's `cid` and
  locally held deposit events, checks the resulting onchain root, and builds the Merkle proof for its
  own note label. The spent label is never requested from the server: the per-label `privacy.asp.proof`
  endpoint was removed. Only label-free requests remain: `privacy.asp.status`, `privacy.asp.set`
  (each pool's current `{ root, cid }`, identical for every caller and used only when device events lack
  that root event), and `privacy.asp.publish`.
- **Publication decisions depend on neither label nor network.** The device requests a new root once
  (`privacy.asp.publish`, no arguments) exactly when operator status reports a due pool root
  (`screening.rootDue` from visitor-wide `privacy.asp.status`, at most two minutes old), unless that
  response's announcements already sharply shrink a pool's newest root by at least max(10, 20%) members.
  In that case no network sends a request, since one response spans every network. For roots with 10 or
  fewer members, announcing all but one is not a sharp shrink, so the request follows the prompt and
  "Withdraw anyway", and the returned root may make those exclusions public. Without that response,
  the legacy open-policy rule applies: `currentASPRoot` differs from the root of all visible deposits.
  Requests occur only after checking the newest root, locating the note in it, and asking the crowd-size
  questions; nothing after the request depends on the note. Simultaneous withdrawals make the same
  decision regardless of the spent deposit, so neither the request nor the subsequent `ASPRootUpdated`
  identifies a deposit. The app never requests publication because "my deposit is not included yet".
  The server publishes due pools concurrently using fresh events (no three-second cache, since requests
  often follow deposits by seconds), waits at most 20 seconds per chain for receipts, and returns each
  pool's status: `published`, `pending` (with transaction hash; later requests do not send a second
  transaction), `current`, `empty`, `no_key`, `not_postman`, `unfunded`, `policy_error` (publication paused;
  nothing sent), or `unavailable`. The device always awaits that response, then its own pool transaction
  on its own network RPC. Relayed withdrawals still name their network: the relayer needs a destination chain.
- **Scheduled publication follows time and operator edits.** Auto-publish does not depend on visitors,
  requests or which deposit will be spent; it reads only public pool data, its own key's balance and the
  operator exclusion list, with an extra tick after a file edit.
- **Server root records are used only after device-side reconstruction, and only for membership.** The
  spent label must exist in device-held events, which also supply its position; server-provided labels
  are never used. If current-root events are missing because RPC logs lag contract reads, the device
  resyncs once. If still missing, it uses the root record already in status (`current.cid`, no new request);
  only a mismatch triggers one argument-free `privacy.asp.set` request. Its pool's `{ root, cid }` is used
  only if it names the current root and reconstructs that root from local events. A root binds membership,
  not the "excluded"/"not yet considered" split, so leaves in a server record's `x` (including status
  `current.cid`) remain operator claims: deposits are held as announced `WAITING`, never `EXCLUDED` with
  a ragequit suggestion. Fake records, such as a `cid` omitting a deposit without listing it, and records
  for another root are rejected (`UNVERIFIED_ROOT`); event gaps get one resync. Sync reads the pool header
  first, then chain head without the Viem cache, so events normally include the root just read.
- **Fail closed, newest root only.** Fixed `resolveAssociationProof` order: (1) root 0 → `NO_PUBLISHED_ROOT`;
  (2) one `isKnownASPRoot(current root)` check; (3) reconstruct/check that root's list, with at most one
  resync and one record request, all label-free; only then (4) examine the label: absent from local events
  → `NOT_MEMBER`, its leaf in the device-held root record's `x` → `EXCLUDED`, not considered → `WAITING`,
  member announced for exclusion → `REMOVAL_ANNOUNCED`. Such notes stop here, before any withdrawal request.
  Next: (5) crowd questions, identical for all notes able to start; (6) label-free publication request if due;
  (7) recheck the onchain root identically. If it removes a deposit from step 5's crowd whose exclusion was
  not announced in the latest status read (an honest exclusion announced one or two minutes earlier also
  stops it), every note stops equally (`SET_CHANGED`: "The association set changed while this withdrawal
  was being prepared …"), so the returned root cannot identify a deposit. Finally, (8) prove, with at most
  one additional question identical for every note; if already prompted before the request, ask only if
  the proof crowd is clearly smaller than the form showed. No fallback to older, smaller roots. An
  unverifiable root yields `UNVERIFIED_ROOT` with a reason: membership does not produce the root,
  unreadable record, `n` falling without listed exclusions despite a matching root (policy violation),
  open-policy root after a screening root (version rollback), or a newer policy version ("This app is
  out of date: reload the page."). A nonmatching membership list is never interpreted as a decrease in
  `n`, so it never makes members appear "Excluded". Ragequit remains available as the public-exit path.
- **Crowd size is visible before sending; sharp shrinkage prompts the user.** The app's crowd is the newest
  root's membership minus members announced for exclusion. Status can differ per visitor, and announced
  members are held by the app, so the operator knows an app withdrawal must come from the remainder.
  The form displays this crowd (`previewAssociationSet`: current root, or a device-reconstructed next-root
  snapshot recipe when due; never just a response's claimed count); operation status shows actual proof
  crowd size. Before any operator-visible request (except an input-free record request that a lagging-log
  device can send immediately after a root change), the device compares with the largest among the last
  16 *distinct*, locally verified root values from its events, searching at most 64 distinct values,
  and with the newest root itself when announcements shrink it: the *shrink alarm*. Copies count once;
  unverifiable values do not count, so bursts, heartbeats and junk roots cannot blind it. A decline of
  at least max(10, 20%) triggers a prompt showing removed deposits, announced-only removals and removals
  without published reasons. It also prompts before any request for fewer than 10 deposits
  (`SMALL_ASSOCIATION_SET`), alongside onchain membership count when some exclusions are announced.
  After a requested root arrives, or when none was requested, it prompts at most once more: if no earlier
  prompt, about a small/sharply reduced proof crowd or one clearly smaller than the form showed; otherwise
  only when clearly smaller (sharp reduction or a lower verdict band). Form figures are identical for
  every note: an operator snapshot is used only if internally consistent (`n` never decreases; `x`
  contains only announced leaves). Without consent, no withdrawal or new-root request reaches the
  operator, relayer or wallet; a lagging-log device may already have made an input-free record request.
- **Deposit status is calculated on the device; only members can withdraw.** "Waiting for screening",
  "Joins next root", "Excluded" (with "Excluded: use the public exit"), "Exclusion announced", "Removal
  announced" and "Checking…" derive from local events, the onchain root, `privacy.asp.status` and deposit
  timing from `privacy.poolActivity`, matched by transaction hash without reading a specific block.
  No request depends on these statuses. Private withdrawals start only for deposits in the newest
  onchain root and not announced for exclusion. Other notes are held and send nothing regardless of
  status response claims (snapshot `n`, delays, revoked exclusions, deposit timing). A per-visitor status
  cannot make one note start and then fail after a publication request in an identifying way; neither
  can the response root, since `SET_CHANGED` stops every note equally. Whether a user retries can still
  reveal information; see *Residual signals*. Operator-only announcements, absent from the onchain root,
  are never authoritative: they can only hold the app and reduce its counted crowd, not mark a deposit
  "Excluded" or suggest ragequit, since responses can differ per visitor and ragequit names the depositor.
- **The relayer rejects old roots containing excluded deposits.** A proof against a noncurrent root whose
  membership includes excluded deposits, or which cannot be reconstructed server-side, is rejected before
  simulation: "The association-set root this proof used is no longer accepted. Nothing was sent; make a
  new proof." The current root is never rejected. Excluded means list entries plus exclusions recorded
  in the current onchain root, so a missing/corrupt list, such as after restart without its file, does
  not disable rejection. With such a list and an unverifiable current root, every older root is rejected
  (fail closed). The response depends only on the root, a public proof signal, and is identical for every
  proof against it. Active; owner approval required (`server/privacy/relayer.ts`, one block).
- **Exclusion list.** The raw file is never served. Only named deposits in served pools become public:
  label, leaf and reason code in `privacy.asp.status`, plus excluded leaves in each permanent onchain
  root `cid`. Notes (`note`), dates (`added`), first server-match times and listed addresses that never
  deposited are never published or logged. Devices calculate late announcements from when they first
  observe them, in memory only while unlocked; Lock, Forget, recovery and new vaults clear that state,
  restarting the count on each unlock. File errors name only entry numbers and fields. Marker notes
  in E2E/server tests verify this.
- **Public data is read identically for every visitor.** Devices sync every build-supported pool's public
  events on opening and every 45 seconds, regardless of vault contents or active network. Every privacy
  page also fetches visitor-wide `privacy.asp.status` on opening and every 60 seconds. Server requests
  have no parameters except the `privacy.pools` chart interval (a Pools-page display choice), and return
  every pool together (`privacy.networks`, `privacy.pools`, `privacy.poolActivity`, `privacy.asp.status`,
  `privacy.asp.set`, `privacy.relayer.quote`). Wallet-address reads (wallet balances) go only to the active
  network's RPC. The privacy wallet configuration enforces this in its transport
  (`client/src/privacy/walletGuard.ts`), for every component. The dashboard account menu shows only
  address, network, Copy address and Disconnect, without balance reads. Other components' balance reads
  are rejected before sending if the wallet network differs from the active network; networks without
  pools receive no requests. Inherent exceptions: `relayer.submit`/`relayer.status` name their network,
  and `privacy.poolDetail` names the pool whose page is being viewed.
- **Privacy checks make no per-note requests.** Deposit/Withdraw guidance (see *Vault privacy guidance*)
  is calculated on the device from already available public data or data fetched identically for every
  visitor: local pool events, public `privacy.pools` summaries already fetched by the dashboard (pool
  size), and public `privacy.poolActivity`. The latter remains parameter-free but returns a list keyed
  by (chainId, pool address) for every pool, each with its own chain's `now`. The device selects the active
  list (`activePoolActivity`, `client/src/privacy/publicData.ts`). The vault page fetches it on opening
  and every 60 seconds regardless of tab, note or form inputs; panels read only that copy. Local events
  identify the note's deposit by label and the public list supplies its time, but only if it names the
  active chain/pool and contains that deposit transaction (`activityStatus`); otherwise checks lack timing.
  No specific-block RPC or application request contains the note's label, value, leaf index, block,
  transaction hash or time. Verified through browser-session request logs on an Anvil pool.
- **Network selection is not stored.** The active network exists only in memory. Internal links may carry
  `#network=<slug>`, e.g. `/pools/vault#network=robinhood-testnet`; it is read once and removed from the URL.
  Selection never enters query strings, local storage or URLs written by the app.
- **The development debug collector excludes privacy areas.** Only in development (`NODE_ENV` is not
  `production`), Vite injects the Manus collector (`client/public/__manus__/debug-collector.js`, writing
  to `.manus-logs/` through `/__manus__/logs`). It is not injected on `/pools`, `/pools/*`, `/privacy`. If a
  session starts elsewhere and enters a privacy area, it records nothing there: no UI events, input or
  selection values, console lines, requests/bodies, or sends while that page is open. Privacy API calls
  (`/api/trpc/privacy.*`) are never recorded from any page; the server also discards matching entries
  before logging (`vite.config.ts`). Production builds contain no collector.
- **Residual signals:** device publication requests and subsequent onchain root updates suggest an
  upcoming withdrawal and that the spent deposit is among unannounced members of the newest root, since
  only members may start, even if proving later uses a larger next root. The app prompts first if that
  crowd is below 10. An operator suspecting a deposit can exclude it onchain around a withdrawal; every
  note stops equally (`SET_CHANGED`), but whether the user retries and succeeds still reveals something.
  The exclusion is public and permanent in the root record. With lagging device RPC logs, a withdrawal
  may request an input-free root record before crowd questions; if the root just changed and excludes
  the note, it stops immediately after that request. Scheduling reduces publication requests. The used
  root is public: without new roots, a withdrawal hides only among current-root deposits. Only recorded
  exclusions can shrink the crowd. A dishonest operator can still publish **one root excluding many
  deposits**, e.g. immediately after a withdrawal requests a root, or tell just one visitor that all but
  one member will be excluded. The shrink alarm prompts before sending and crowd size remains visible.
  It compares the last 16 distinct, locally verified event roots, so neither an eviction burst filling
  16 slots with current-root copies nor 16 junk roots blinds it. An operator must first publish 16
  distinct, small, verified roots, each with public mass exclusions/records, or more than 64 consecutive
  distinct root values, to evade it. These checks assume device RPC is not controlled by the operator.
- **The 16-root window.** After removal, older roots containing that deposit remain accepted until 15
  more roots are posted after the removal root. Hylsia's app/relayer stop using them; self-submitting,
  self-funded clients still can. An opt-in *eviction burst* (`npm run zk:asp:publish -- --chain <id> --evict`,
  then `--evict --yes`) closes the window by reposting the current root. Bursts can run alongside the
  server: before each post they wait for no pending postman transaction, reread the latest root/record,
  and send with an explicit nonce, so old roots/records do not overwrite newer ones. Exception: nodes
  with fee-based pending-transaction replacement, such as Anvil/Geth, can replace a much cheaper pending
  newer post with a burst post; the server republishes that root after 10 minutes. Both use the same RPC
  fee estimate, so the burst post is normally rejected instead. A burst post unmined after 120 seconds
  stops the burst with an explanatory message. Measurements, costs and proposals: `docs/privacy-pools/asp-window.md`.
- **No sign-in or session cookies anywhere.** No page requests a sign-in signature or uses a server
  session. Legacy trading pages (`/trade`, `/strategies`, `/login`), wallet sign-in and session cookies
  were removed in the 2026-11-17 cleanup. The server neither reads nor sets cookies; tRPC context contains
  only request/response. Every tRPC call, including landing-page calls, and artifact download omits
  cookies (`credentials: "omit"`). No `privacy.*` procedure requires a session.
- **One app-wide wallet configuration: MetaMask and Rabby (EVM).** Landing (`/`, including unknown paths),
  `/pools`, `/pools/*`, `/privacy` use `client/src/privacy/wagmi.ts`, storage key `hylsia.pools.wagmi`;
  routing is in `client/src/areas.ts`. Previously authorized wallets reconnect on landing too, without
  mainnet reads: only build-supported networks, no mainnet/ENS lookups, guarded transport. *Connect a
  Wallet* offers only **MetaMask** and **Rabby Wallet** through their injected EVM providers, without
  WalletConnect relays or the MetaMask SDK. Unrestricted EIP-6963 connector discovery is disabled;
  `evmWallets.ts` uses local announcements only for these identities and rejects Phantom providers,
  including those claiming MetaMask compatibility. The selected provider stays an in-memory connector
  reference, so changes to default `window.ethereum` cannot redirect switches/transactions to another
  extension. Phantom connector history is not restored; reload and choose MetaMask/Rabby if disconnected.
  Discovery and opening the selector request no accounts or RPC. This is the app's only wallet
  configuration; the old trading configuration remains removed. `OnchainProvider.tsx` supplies React
  providers and the RainbowKit theme. `/trade`, `/strategies`, `/login` still show the landing page.
- Secrets exist only in client-session memory. Local storage holds the encrypted vault
  (`hylsia.pp.vault.v2`), public-event caches and per-pool deposit-index reservations
  (`hylsia.pp.<chainId>.<pool address>.*`), plus one device activity log (`hylsia.pp.activity.v3`; each entry
  names its network). Because this log pairs deposits with withdrawal recipients, it is **encrypted
  using a vault-seed-derived key** (`client/src/privacy/activityStore.ts`): HKDF-SHA256 over the 32-byte
  seed, fixed salt and info `hylsia-activity-log:v1` produces a nonexportable AES-256-GCM key held only while
  unlocked and discarded on Lock/Forget; the seed itself is never stored. The storage key holds only an
  envelope `{format:"hylsia-activity",version:1,iv,ct}`, with a fresh random 12-byte IV per write and
  additional data binding format, version and vault fingerprint, so other-vault or tampered logs fail
  decryption. Cross-tab Web Locks make read/decrypt/merge/encrypt/write and migration atomic; distinct
  entries merge and the latest update per ID wins. Deposit-index reservations use the same encryption
  key/envelope (format `hylsia-pending-deposits`; additional data also binds chainId/pool), retaining
  indices/transaction hashes and a watermark for the last index released from pending. The encrypted
  watermark prevents stale tabs reusing indices. Reservations this vault cannot decrypt (another vault,
  tampered or corrupt) are never deleted/overwritten; deposits in that pool stop with an explanation.
  Before unlock, logs are neither read nor displayed; pending activity is rechecked after unlock. On
  unlock, legacy plaintext logs (`hylsia.pp.activity.v2`, including startup `migrate.ts` results from
  per-pool keys, and this vault's single-network-build `hylsia.pp.<chainId>.<pool address>.activity` logs)
  merge by entry ID, are written encrypted, and are deleted only after successful writing. Unparseable
  plaintext logs are deleted without reading their contents, with an Activity-panel notice. Undecryptable
  v3 logs (tampered, corrupt or another vault) move unread to `hylsia.pp.activity.quarantine`; a new empty
  log starts and Activity shows a short notice. Encryption protects stored logs, not against someone
  using an unlocked vault. Still visible: log size; per-pool reservation keys during unfinished deposits,
  including interrupted deposits awaiting wallet answers (indices stay reserved in case the wallet still
  submits, until Forget/new vault/recovery); and, only in local testing, another vault's old single-network
  per-pool log remains plaintext until Forget/new vault/recovery. Lock requested during an operation takes
  effect immediately after completion and recording with the vault key; the Lock button says so. Forget
  acts immediately: an operation may still finish onchain, but nothing further is saved on this device.
  Tabs whose vault was forgotten/replaced in any tab make no more writes. Every log form is cleared by
  "Forget vault on this device", new-vault creation and restoring another vault. Forget clears all vault,
  activity (v2/v3/quarantine) and pending-deposit `hylsia.pp.*` keys while retaining public-event caches;
  `hylsia.pools.wagmi` wallet connections remain. They contain connector/address, never actual network:
  stored chain IDs are normalized to the build's first network, identical on every device, so locked or
  forgotten devices do not reveal the last wallet-operation network. Reconnection reads the live wallet network.
- Proving artifacts are SHA-256-verified against `manifest.json` before use (`client/src/privacy/artifacts.ts`).
- **Every transaction is signed for its operation's chain.** The app passes that chain to Viem, not the
  wallet's current chain; Viem checks immediately before sending and rejects a mismatch with
  `ChainMismatchError`. Receipts come from the operation-chain RPC. Deposit targets come only from the
  built-in registry, never URLs/server responses. Operation states: `preparing`, `awaiting_wallet`,
  `downloading`, `proving`, `submitting`, `pending`, `confirmed`, `failed`. After reload, pending activity
  resumes on unlock because the log is unreadable beforehand: await receipts for up to 300 seconds on
  its chain, search the hash on other build-supported networks, then fail with an explanatory result.
  Deposit-index reservations release after settlement; entries without a transaction close with a
  page-reload explanation. These checks retain no log key, await receipts in 15-second rounds and stop
  on Lock/Forget after the active round; the next unlock restarts them.
- **Networks without pools are not contacted.** Until deployment, neither server nor device calls that
  network's RPC (zero calls); `privacy.pools`/`privacy.poolActivity` use server time for it, avoiding RPC
  errors in pending status. Misconfigured networks (invalid address, pool without deploy block, Anvil
  record, scope mismatch) report *unavailable*, not "not deployed", and are not contacted either.
- **VITE_ values are public in the bundle; never put secret keys in VITE_ RPC URLs.**
- **Analytics never runs in privacy areas.** With `VITE_ANALYTICS_ENDPOINT` and `VITE_ANALYTICS_WEBSITE_ID`
  set, Umami loads only on the first nonprivacy page view, outside `/pools`, `/pools/*`, `/privacy`;
  privacy-first visits never contact analytics. Automatic tracking/history hooks are disabled, so
  `#network=` vault links are invisible to it. Only nonprivacy page paths are sent, without queries or
  fragments (`client/src/analytics.ts`).

## Resilience (Phase 5)

- **Connection settings** (server icon in the dashboard header): two browser-owned choices stored only
  locally (`hylsia.pools.rpc.v1`, `hylsia.pools.relayers.v1`, outside `hylsia.pp.` so Forget vault retains
  them), never sent to Hylsia's server.
  - **Custom per-network RPC** (`client/src/privacy/rpcOverride.ts`): every vault read (event sync,
    contract reads) uses this endpoint; before use it must answer the network's `eth_chainId` from the
    browser. It never enters the chain `rpcUrls` passed to the wallet; dashboard figures still come from the server.
  - **Relayer** (`client/src/privacy/relayers.ts`): "This site", build-listed (`VITE_PRIVACY_RELAYERS`), or
    user-added (another Hylsia server). A withdrawal requests its quote and submits to the relayer chosen
    at startup, never another; its fee is proof-bound. List status is fetched only when settings open.
    Invalid quotes are rejected; a refreshed fee may not exceed the amount shown when Withdraw was pressed.
    No automatic retry through another relayer. `server/privacy/relayerCors.ts` serves other sites' withdrawals.
- **Static pool snapshots** (`shared/privacy/snapshot.ts`, `npm run zk:snapshot`): writes
  `client/public/snapshots/<chainId>-<pool>.json` from public data without keys, first checking its tree
  root against the pool. A device without a pool copy starts from this file. It contains only deposits
  and withdrawals, with deposit commitments recomputed. Chain ID, block hash, SCOPE, root and leaf count
  must match the pool at the exact checkpoint; the tree plus later blocks must produce a known pool root.
  Ragequits and association-set roots never come from snapshots: immediately afterward the device reads
  their complete history in the background ("Reading history") and holds private withdrawals until done.
  Snapshot-derived copies are never cached; any failed check discards the snapshot and scans from deploy
  block. RPC without historical-state access also uses a full scan. RPC/remote-relayer calls omit cookies
  and referrers and reject redirects; same-origin Hylsia RPC endpoints are rejected before contact.
- **Phase 5 checks (18 November 2026):** `npm run check`, 487 unit tests (20 files), 24 contract tests,
  `npm run zk:e2e` (74 seconds), and `npm run build` passed. E2E checks real Anvil checkpoints, rejects
  tampered/incomplete/cross-chain snapshots, and recovers change notes from snapshots plus new events.
  Unit tests use fetch-recording RPC transports and relayer clients to check destination origins,
  cookies, referrers, redirects and fee caps. The live-pool snapshot was created from public reads through
  block 155019673; no deposits yet. Chrome production-preview checks also covered settings and same-origin
  RPC rejection, with the publisher off.

## Running

Proving artifacts (`client/public/zk`) and verifiers (`contracts/src/verifiers`) are already built and
match; the live pool uses this set (16 November 2026 build). **`npm run zk:build` is not a routine step**:
a new build makes the live pool reject every proof; see *Rebuilding circuits*.

```bash
# 1. Contracts and tests
npm run zk:contracts:build
npm run zk:contracts:test   # 22 PrivacyPool tests with real proofs + 2 CrossChain tests (cross-chain proofs rejected)
npm test                    # vitest (server/**/*.test.ts)

# 2. Complete local prototype on two automatically started/stopped Anvil nodes: chain A uses
#    Robinhood Chain Testnet ID 46630; chain B uses local chain B (31338), exercising multi-network code.
#    Deploy on both (same pool address, different SCOPE) → deposit → publish root → device association proof
#    → relayer → v2 backup recovery → ragequit, plus fail-closed and negative cross-chain checks;
#    unfunded relayer/publisher reporting without sends, then one scheduled tick after funding.
#    Screening (chain A, one-hour delay via Anvil time travel): delay boundaries, pre-screening exclusions,
#    post-inclusion removal, the 16-root window measured root by root, opt-in eviction bursts, revoked
#    exclusions, invalid lists, another publisher's roots, shrink alarms, newer policy versions.
#    Since review round 2: announce all but one member (or leave 9), prompt before any request;
#    response roots removing unannounced members stop withdrawals (SET_CHANGED); 16 junk roots cannot
#    blind the shrink alarm; no exclusion notes or keys appear in any response or log.
npm run zk:e2e              # ports: E2E_ANVIL_PORT_A (default 8547), E2E_ANVIL_PORT_B (default 8548)
```

`npm run zk:fixtures` regenerates real proofs for Foundry tests (`contracts/test/fixtures/pool.json`,
chain 31337) from `circuits/build` keys. It is needed only after a circuit rebuild and changes neither
verifiers nor artifacts.

### Deployment

The Robinhood Chain Testnet pool is already deployed; see *Live pool*. These steps are for a replacement
pool or a future registry network. Always start with a dry run; transactions need an operator key
funded with test ETH.

```bash
# 1. Default dry run: check RPC/chain ID, then simulate the complete deployment as the deployer address.
#    Address only; no key or balance needed. No transaction or deployment record is created.
npm run zk:deploy:robinhood -- --sender 0x<deployer-address>

# 2. Once: create a Forge deployer keystore (safer than a key in .env), then fund it with test ETH
cast wallet import hylsia-deployer --interactive

# 3. Actual deployment: --broadcast with the wallet. Verify contracts on Robinhood Chain Testnet Blockscout.
npm run zk:deploy:robinhood -- --broadcast --account hylsia-deployer --sender 0x<deployer-address>
```

Because `contracts/deployments/46630.json` already exists, step 3 is refused unless `--replace` is added.
With `--replace`, the app serves the new pool; old-pool notes remain there and can exit only through the old pool.

Other `scripts/privacy/deploy.ts` options: `--ledger --sender 0x…` (Ledger), `--rpc-url <url>` (or
`PRIVACY_DEPLOY_RPC_URL_<id>`; otherwise that network's public RPC), `--no-verify`, `--replace`,
`--gas-estimate-multiplier <percent>`. `PRIVACY_DEPLOYER_PRIVATE_KEY` can replace the keystore.
Owner, postman and minimum deposit come from `PRIVACY_POOL_OWNER`, `PRIVACY_ASP_POSTMAN`,
`PRIVACY_MIN_DEPOSIT_WEI`. Only RPC hosts are ever printed.

Checks before Forge and subsequent behavior:

- **Rejections:** loopback RPC (use `npm run zk:deploy:local`/`npm run zk:e2e` for local chains), wrong RPC
  chain ID, an existing `contracts/deployments/<id>.json` without `--replace`, or verification keys that
  differ from another public registry pool in the build (the registry at this implementation stage
  contains only one public network).
- **Forge environment:** always passes `--rpc-url`, `--chain <id>`, `--slow`. Removes `ETH_RPC_URL`, `CHAIN`,
  `CHAIN_ID`, `VERIFIER`, `VERIFIER_URL`, `PRIVACY_DEPLOYMENT_OUT`, every `FOUNDRY_*`/`DAPP_*` variable
  (e.g. `FOUNDRY_LIBRARIES`, `FOUNDRY_PROFILE`, `FOUNDRY_ETH_RPC_URL`) through `forgeChildEnv`, also in E2E.
  These cannot redirect deployment to another chain/verifier, link an existing Poseidon library, or
  alter bytecode and thus CREATE2 library addresses.
- **`Deploy.s.sol` guards:** reject Forge's default sender and, outside Anvil, the ten default Anvil
  accounts as deployer, owner or postman. Deployment records, including `protocol`/`deployer`, are written
  only with `--broadcast`; dry runs print "dry run: no deployment record written".
- **Contract verification** follows broadcast automatically on Robinhood Chain Testnet Blockscout
  (`https://explorer.testnet.chain.robinhood.com/api/`, no key).
- **Sync:** after broadcast, `sync-deployments --check-onchain --chain <id>` checks the new pool onchain
  and writes `shared/privacy/deployments.ts`. Rebuild/restart the app afterward; server and browser read
  the pool from that file.
- **Broadcast failure:** `Deploy.s.sol` writes its record during script execution before Forge sends.
  `deploy.ts` therefore checks whether the recorded pool exists onchain. If absent, it removes the new
  record or restores the previous one, leaving no false record. If present, Forge failed after deployment,
  usually at explorer verification, so sync still runs; repeat verification with *Manual contract verification*.
  Sent library/verifier transactions have already advanced the deployer nonce, so redeploying changes the pool address.
- **Gas on chain 46630:** Forge does not recognize it ("Unsupported Chain IDs"); if a transaction runs
  out of gas, retry with `--gas-estimate-multiplier 200`.
- **One build.** Deploy from one frozen build/checkout: compilation metadata changes Poseidon CREATE2
  library addresses. `contracts/src` is deployed but not yet Blockscout-verified (pool and both verifiers);
  do not change it, including NatSpec still naming the old planned network, since that changes metadata
  and bytecode. Full verification publishes that NatSpec on the pool explorer page, so whether/how to
  verify the live contract is an owner decision. Do not run zk:build between deployments.
- **Slow connections:** `.npmrc` gives Node one second per connection attempt
  (`node-options=--network-family-autoselection-attempt-timeout=1000`); `server/_core/loadEnv.ts` does the
  same for server/scripts. Otherwise a testnet RPC taking 0.4–0.5 seconds to connect is aborted after
  250 ms ("could not read eth_chainId … HTTP request failed."). When invoking `npx tsx` or `node` directly
  without loadEnv, set `NODE_OPTIONS=--network-family-autoselection-attempt-timeout=1000` yourself.

### Deployment records

- `Deploy.s.sol` writes `contracts/deployments/<chainId>.json` only with `--broadcast`. On Anvil using
  a nonlocal chain ID (not 31337/31338, e.g. Robinhood Chain Testnet 46630), records go into
  `contracts/deployments/local/`, ignored by Git and sync, so a local chain never appears as a real pool.
  `PRIVACY_DEPLOYMENT_OUT` overrides the location, as used by E2E.
- `npm run zk:deployments:sync` reads only the top level of `contracts/deployments/` (local 31337/31338 only
  with `--include-local`, used by `zk:deploy:local`) and validates every record: filename = `chainId`,
  all fields present, checksummed addresses, `scope = computeScope(pool, chainId)`, and for public networks,
  no default Anvil deployer/owner/postman and a deploy block above zero. It merges libraries, transaction
  hashes and successful (`0x1`) pool receipt blocks from
  `contracts/broadcast/Deploy.s.sol/<id>/run-latest.json`, pins verification-key SHA-256 digests from
  `client/public/zk/manifest.json`, and checks onchain `eth_chainId`, pool code, `SCOPE()`, and each
  verifier's code hash against compiled bytecode. A mismatch reports "the served proving keys no longer
  match the deployed verifiers". One bad record stops sync without writing anything.

### Rebuilding circuits (not a routine step)

Every `npm run zk:build` creates a new random trusted setup, replacing `contracts/src/verifiers` and
`client/public/zk` together. The live pool retains its old verifiers and rejects every new-artifact proof.
The script therefore refuses while a public-network deployment record exists, as it does for the live
pool, unless `--force` is supplied, intended only for retired pools. After rebuilding, run
`npm run zk:fixtures` so Foundry tests use proofs from the new keys.

## Known limitations and next steps

1. **Development trusted setup.** One local phase-2 contribution and local ptau. Before real-value assets:
   public-ceremony ptau + multiparty phase-2 ceremony, transcript verification, and `vkey`/verifier-bytecode matching.
2. **Unaudited.** Circuits, contracts, key management and configuration require independent review (phase 4),
   including before Robinhood Chain mainnet.
3. **Indexing.** Static snapshots accelerate initial sync; devices still read full history from their chosen
   RPC before private withdrawals. High volume requires an indexer.
4. **ASP.** Screening policy v1 (Phase 4) is a testnet policy: one-hour inclusion delay and operator exclusions.
   No production operator or external review yet; screening is only as good as its list (unreported deposits enter).
   New roots come from the server's scheduled publisher (default every 10 minutes and immediately after
   member-removing edits), label-free device requests before withdrawals, or `npm run zk:asp:publish`.
   Without publisher keys/funds, roots remain old; deposits absent from the current root wait (`WAITING`).
   Devices reconstruct each root's membership from its `cid` recipe and their events, and prove only against
   the newest root. Remaining limits: the 16-root removal window for self-funded clients
   (`docs/privacy-pools/asp-window.md`; manual eviction bursts, automation awaiting owner decision); shrink
   alarms can be evaded by first publishing 16 distinct small verified roots, each with public mass exclusions,
   or more than 64 consecutive distinct root values; at most 500 exclusions per pool (more requires policy v2);
   one publisher/code version/list per pool; device event caches grow with every `cid`.
5. **Relayer.** One relayer currently operates. Phase 5 supports manually listing/selecting alternatives;
   no automatic failover. If unavailable, the UI offers self-submission with a visible gas payer.
6. **Statistical privacy.** Quiet pools, distinctive amounts and close timing still allow correlation. The UI
   warns about recipients matching connected wallets or previous deposit addresses, suggests standard deposit
   amounts and displays a pre-withdrawal privacy check. This public-data heuristic is not a guarantee: IP
   addresses, cross-application behavior and offchain data may narrow crowds further. Summing withdrawals from
   one deposit is warned about, not modeled. The live pool is still empty; its crowd grows only with deposits.
7. **No in-pool transfers or selective payment proofs yet** (phase 6).
8. **One pool, one crowd.** Other pools, e.g. future Robinhood Chain mainnet or ERC-20 contract variants, have
   separate crowds; one pool's deposits never enlarge another's anonymity set. A second same-network ETH pool
   is discouraged because it fragments the crowd.
9. **Gas.** Deposits ~0.99 million, withdrawals ~1.13 million: inexpensive on Robinhood Chain Testnet at
   0.01 gwei, but mainnet costs need reassessment.
10. No retired-pool directory yet.
11. **Wrong-network deposits.** The app specifies every operation's chain and Viem rejects wrong-chain wallets,
    but deposits still sent elsewhere, e.g. through another tool, are not found by note scanning; recovery is unsupported.
12. **Activity logs are encrypted, not completely hidden.** Since Phase 3, logs and deposit reservations use
    seed-derived encryption. Log sizes and per-pool reservation keys remain visible during unfinished deposits,
    or after interruption before a wallet answer until Forget. Anyone using an unlocked vault can read the log.
    Two unlocked tabs with the same vault each write their own log copy, so the last write wins.
13. **Robinhood Chain mainnet.** Not yet: the same contract/app would need deployment and a registry entry,
    but real funds call for an audit first.

### Vault privacy guidance

The whitepaper calls for an interface that recommends standard amounts and waiting periods, and for small
anonymity sets, standard amounts, UI warnings and pool size before each action. A separate guidance page
was removed because it resembled a liquidity tool; guidance now lives in vault forms.

Every guidance figure (pool size, standard amounts, deposit rate/timing) comes only from the active pool,
selected on-device by (chainId, pool address); other pools are never aggregated. If that pool's activity
list is unavailable, timing is unavailable and no verdict is given.

- **Deposit.** Pre-action pool size comes from the active entry in public `privacy.pools`, without a
  device-side tree rebuild: *Anonymity set* (published-root deposits, `aspRootMembers`, matching the
  dashboard) and *All deposits*, with "Checking…" until available. Standard-amount chips
  0.01 · 0.05 · 0.1 · 0.5 · 1 · 5 ETH (`STANDARD_LADDER`; a banknote-style 1–5 ladder with few rungs to cluster
  deposits, starting at pool `minDeposit`) fill the amount field and show other deposits using that exact
  amount ("used by 12 others"). This vault's/connected wallet's deposits appear separately as "+1 yours";
  ragequit deposits do not count. Chip counts/warnings wait for ready pool status. Standards protect only
  when others use them: fewer than 10 others gives a soft note ("Only 2 other deposits used 0.5 ETH so
  far…; plan to withdraw a part"). Unusual amounts, neither standard nor used by at least 10 others,
  receive a rose-colored warning: a later exact-value withdrawal or one larger than other deposits may
  identify yours. *Use … ETH* suggests only a standard used by more other deposits than the typed amount:
  the most used at/below it, otherwise the most used at/above `minDeposit`, otherwise no suggestion.
- **Withdraw.** *Privacy check* sits immediately before Submit. Its numeric rows show the proving
  association set (one sentence, e.g. "Counted once the next root is posted; the current root covers
  115."), members large enough to fund the amount, exact-amount crowd for full original-deposit spends
  (hop 0), deposits since yours and elapsed time, *effective anonymity set* and verdict (linked ≤1,
  weak <10, moderate <50, strong ≥50), plus suggested waiting time. Reasons below give advice without
  repeating row figures. The observer model combines exact-amount and timing tests for full original
  spends (matching-amount deposits inside the time window), estimating the smallest crowd. Waiting time
  is the smallest `WAIT_STEPS` value projecting ≥50 at that pool's own rate: other deposits/day over the
  last 7 days or since its first deposit if younger, measured over at least one day. The last step shows
  "Within 30 d" (14–30 days); beyond it, "Over 30 d"; below one other deposit/week, "Too quiet to project".
  If the limiting crowd cannot grow because no others match or can fund the amount, show "Waiting does
  not help here: withdraw a part instead." or "withdraw X ETH or less", with *Use … ETH*. Current time is
  the active pool's public chain `now` plus time since fetch, not device-clock time. Without public timing
  (loading/failed/wrong-pool list or missing note deposit), show no verdict, estimate, summary or wait:
  only timing-independent figures and "Checking timing…" or "Timing could not be checked, so this check
  is incomplete. A recent deposit is easy to link by timing." Never Strong without timing checks.
  Strong-estimate summary: "By this estimate, an observer is left with about N plausible deposits."
  Full-original spends suggest a standard partial amount via *Use … ETH*, leaving change; no other
  sufficiently large deposits produces "Withdraw X ETH or less." with *Use X ETH*. This vault's and the
  connected wallet's other deposits are excluded from the crowd: linking one links all. A recipient
  matching the connected wallet/a vault deposit address, or a gas-paying wallet that made a vault deposit,
  makes the verdict *Linked*. Show the cause directly below it and hide amount/exact-value/timing/wait
  suggestions because they cannot fix that link. Over-note amounts show "More than this note holds
  (X ETH).", disable Submit and hide negative-change rows. Recipient/self-paid-gas/small-set warnings
  appear once in the same block; the small-set dialog remains. Everything else remains advisory:
  no new blocking behavior.
- **Pool page.** *Privacy health* uses the same ladder ("Standard amounts", `standardAmountShare` in
  `server/privacy/pools.ts`), replacing the old multiple-of-0.01-ETH test.
- **Screening (Phase 4).** Screened sets are no longer deposit prefixes, so privacy checks use positions
  in the proving set (`members`: current root, or next root if due), not all deposits. Wait projections
  count new deposits only after their delays and never end before the user's own eligibility
  (`eligibleAt`). Deposit gives a soft delay note ("A new deposit can be withdrawn privately about 1 hour
  after it is confirmed, unless it is excluded."). Withdraw holds notes absent from the newest onchain
  root (delayed, waiting for next root, excluded, being reinstated, unverified root) or announced for
  exclusion, before anything is sent.

`shared/privacy/simulate.ts`; active-pool selection: `client/src/privacy/publicData.ts`

`server/privacy/simulate.test.ts`, `server/privacy/pools.test.ts`, `server/privacy/publicData.test.ts`.
